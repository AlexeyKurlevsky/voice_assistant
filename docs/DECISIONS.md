# Ключевые решения (ADR)

Документ фиксирует архитектурные и инженерные решения: контекст, само
решение, альтернативы и последствия. Формат — облегчённый ADR.

---

## ADR-1. Слои и инверсия зависимостей (ports & adapters)

**Контекст.** Бизнес-логика не должна зависеть от CLI, PostgreSQL и внешних
API, чтобы их можно было менять и тестировать изолированно.

**Решение.** Три слоя с зависимостями «только внутрь»:
`domain` → `application` (use cases + порты) → `infra` (адаптеры).
`cmd/main.go` собирает конкретные реализации и внедряет их в `application`.
`cli` — тонкий презентационный адаптер, вызывает только `application`.

**Альтернативы.**
- *Плоская структура `main.go` + `storage.go` + `api.go`* — быстрее стартовать,
  но бизнес-логика протекает в транспорт, тестировать сложно.
- *`internal/service` + `internal/handler` без явных портов* — работает,
  но заменяемость внешних клиентов становится «по договорённости», а не
  по контракту.

**Последствия.** Больше файлов и `_repo.go`-обёрток. Плюс: unit-тесты
не требуют БД; замена `mock → whisper` — одна строка в `main.go`
(через фабрику по env).

## ADR-2. `sqlc` + `pgx/v5` вместо ручного `pgx` или `database/sql`

**Контекст.** Нужен типобезопасный слой БД без «магии ORM». Запросы
должны оставаться явным SQL, чтобы контролировать индексы и `tsvector`.

**Решение.**
- SQL пишется в `queries/*.sql`, `sqlc generate` компилирует в `sqlcgen/`.
- `sql_package: "pgx/v5"` — сгенерированный код работает поверх `pgx`.
- `sqlcgen/` коммитится; CI проверяет актуальность через `sqlc diff`.
- Обёртки `*_repo.go` маппят `sqlcgen.*` в `domain.*` и `pgx.ErrNoRows →
  domain.ErrNotFound`.

**Альтернативы.**
- *`database/sql` + ручной `Scan`* — много boilerplate, лёгкие опечатки
  в порядке колонок не ловятся компилятором.
- *`pgx` + ручной `Scan`* — то же, но с `pgx`-типами; быстрее, чем
  `database/sql`, но всё равно ручной маппинг.
- *GORM / ent* — скрывают SQL, плохо сочетаются с `ts_headline` и точным
  контролем индексов; для проекта с фокусом на PostgreSQL — лишний слой.

**Последствия.**
- Плюс: типобезопасность, `WithTx` для транзакций, явный SQL.
- Минус: нужен `schema.sql`, синхронизированный с миграциями; `ts_headline`
  может потребовать override или ручного `pgxpool.Query`.

## ADR-3. `mock` по умолчанию, `whisper`/`openrouter` через фабрику

**Контекст.** Внешние API могут быть недоступны (ключи, квоты, локальная
разработка). Бизнес-логика не должна зависеть от конкретного провайдера.

**Решение.** Интерфейсы `SpeechClient` и `LLMClient` в `application/ports.go`.
Реализации — `infra/speech/{mock,whisper}.go`,
`infra/llm/{mock,openrouter}.go`. Выбор — через
`MS_SPEECH_PROVIDER` и `MS_LLM_PROVIDER` в фабриках
`infra/*/factory.go`.

**Альтернативы.**
- *Только реальный API* — не работает без ключей, сложно тестировать.
- *Только mock* — не демонстрирует заменяемость.
- *Флаги в коде (`if os.Getenv(...)` в бизнес-логике)* — протекает инфра,
  нарушает инверсию.

**Последствия.** Три файла вместо одного на каждого клиента. Плюс: тесты
и демо работают без сети; переключение на реальный API — одна env.

## ADR-4. Модель статусов из 6 значений

**Контекст.** Нужно отразить полный жизненный цикл: создание, работу,
транскрипцию, выжимку, готовность, ошибку.

**Решение.** `created → processing → transcribed → summarized → completed`,
ветка `failed` из любого нетерминального. Все переходы — в транзакции,
каждый пишется в `status_history`. Терминальные — `completed`, `failed`.

**Альтернативы.**
- *Слить `summarized` и `completed`* — теряется наблюдаемость: не видно,
  был ли LLM успешен и сохранён ли результат, или упал между шагами.
- *Добавить `finalizing`* — избыточно, `completed` уже означает
  консистентность.

**Последствия.** Один лишний `UPDATE` + `INSERT status_history` на задачу.
Плюс: видно, на каком шаге упало; при рестарте `summarized` не требует
повторного вызова LLM.

## ADR-5. Каждый переход статуса — в транзакции

**Контекст.** `UPDATE status` без записи в `status_history` может привести
к «фантомной» истории при падении между запросами. Для `MarkProcessing`
и `MarkCompleted` историю можно было бы опустить, но тогда теряется полнота.

**Решение.** Все шесть переходов — в транзакциях (`pgxpool.Begin` +
`WithTx`). `status_history` пишется всегда, включая `created → processing`
и `summarized → completed`.

**Альтернативы.**
- *Одиночный `UPDATE` без истории для «простых» переходов* — быстрее,
  но история становится неполной.
- *Триггер на `processing_tasks` для `status_history`* — работает, но
  скрывает логику из кода; отладка сложнее.

**Последствия.** Чуть больше кода в репозиториях. Плюс: полная история,
предсказуемое поведение при сбоях.

## ADR-6. `tsvector('simple')` + GIN вместо `ILIKE` / `pg_trgm`

**Контекст.** Нужен поиск по транскрипциям и выжимкам, с учётом прав.
Данные преимущественно на русском, но возможны смешанные тексты.

**Решение.** `to_tsvector('simple', text)` + GIN-индексы. Поисковый
запрос — `websearch_to_tsquery('simple', $1)`, сниппет — `ts_headline`.

**Альтернативы.**
- *`ILIKE '%kw%'`* — не использует индексы (кроме `pg_trgm`), не даёт
  сниппетов, не масштабируется.
- *`tsvector('russian')`* — стемминг лучше, но словари зависят от локали
  PostgreSQL и сложнее в тестах; переход — одна миграция.
- *`pg_trgm` + `GIN`* — работает и для частичных совпадений, но не даёт
  ранжирования и сниппетов; обычно комбинируют с `tsvector`, а не вместо.

**Последствия.** Точный поиск по словоформам («бюджет» ≠ «бюджета»).
Для типичных запросов приемлемо. Переход на `russian` — миграция + пересоздание
индекса, без изменения кода.

## ADR-7. `ErrNotFound` вместо `ErrForbidden` для чужих встреч

**Контекст.** Пользователь запрашивает встречу по ID. Если встреча
принадлежит другому — что вернуть?

**Решение.** `domain.ErrNotFound`. Не подтверждаем существование чужих
объектов.

**Альтернативы.**
- *`ErrForbidden`* — информативнее для отладки, но подтверждает существование
  ресурса. Для API, отдающих данные по ID, — стандартная уязвимость.

**Последствия.** «Слепая» отладка: пользователь не знает, встреча
не существует или принадлежит другому. Логи содержат реальную причину
(через `user_id` и `meeting_id`), и разработчик может разобраться.

## ADR-8. Bounded worker pool с `ErrQueueFull`

**Контекст.** Обработка файлов долгая; при массовой загрузке нельзя
плодить неограниченные горутины.

**Решение.** `chan int64` с буфером `JobQueueCapacity`, `N` воркеров.
`Enqueue` — неблокирующий `select` с `default`. При полном канале —
`domain.ErrQueueFull` (exit 3), задача помечается `failed` с `"queue full"`.

**Альтернативы.**
- *Блокирующий `Enqueue`* — `load` ждёт, пока освободится место; плохо
  для UX.
- *Неограниченные горутины* — OOM при шторме загрузок.
- *Внешняя очередь (RabbitMQ/Kafka)* — overkill для одной машины.

**Последствия.** Пользователь получает явную ошибку при перегрузке,
а не «зависание». Размер очереди и число воркеров — в env, регулируются
без пересборки.

## ADR-9. `--limit` / `--offset` для `list` с дефолтом 50

**Контекст.** Со временем у пользователя накапливаются сотни встреч.
Выводить всё в CLI — плохо.

**Решение.** `list --limit N --offset M`, дефолт `50 / 0`, максимум `500`.

**Альтернативы.**
- *Без пагинации* — просто, но неудобно при росте данных.
- *Курсорная пагинация (`created_at < cursor`)* — эффективнее для больших
  объёмов, но сложнее в CLI (нужно помнить курсор между вызовами).

**Последствия.** Пользователь явно управляет окном. Индекс
`(user_id, created_at DESC)` поддерживает `ORDER BY` + `LIMIT`.

## ADR-10. `.env` через `godotenv`, приоритет у env процесса

**Контекст.** Нужно удобно держать дефолты локально и переопределять
в CI/проде.

**Решение.** `godotenv.Load` читает `.env` (не перезаписывает уже
установленные переменные). Далее — `os.Getenv` с дефолтами в `config.Load`.

**Альтернативы.**
- *Только env* — неудобно локально (простыня `export` в каждом терминале).
- *Только `.env`* — неудобно в проде (файл надо монтировать).
- *Viper + YAML* — гибче, но лишняя зависимость для 20 переменных.

**Последствия.** Стандартный приоритет: дефолт → `.env` → env процесса.
`.env.example` в репозитории как документация.

## ADR-11. `schema.sql` рядом с миграциями

**Контекст.** `sqlc` не умеет читать миграции — ему нужна конечная схема.

**Решение.** `internal/infra/postgres/schema.sql` — кумулятивное
состояние схемы. При добавлении миграции `000N_*.sql` — синхронно
обновляется `schema.sql`. CI (`sqlc diff`) ловит рассинхрон `schema.sql`
и `sqlcgen/`, но **не** ловит рассинхрон `migrations/` и `schema.sql` —
это дисциплина разработчика (описано в `DATA_MODEL.md` §6.2).

**Альтернативы.**
- *Генерировать `schema.sql` из свежей БД (`pg_dump`)* — точнее, но требует
  поднятой БД в момент генерации. Для проекта такого размера — overkill.
- *Хранить схему только в `sqlc.yaml` в виде инлайн-строк* — плохо
  читается и не переиспользуется.

**Последствия.** Два файла, описывающих схему. При аккуратной дисциплине —
проблем нет; при спешке — возможен дрейф.
